# Follow-ups

Known gaps, open questions and ideas that were weighed and set aside, with the reason each one is still here. Items come from the round-3 to round-6 code reviews and the CPU work; none of them blocks a release. Open an issue before picking one up so the discussion has a home.

## Needs a product decision

- **What "1 + N" means for N > 5.** The layouts 1 + 7, 1 + 9, 1 + 11 and 1 + 15 put the hero on a square (k + 1) × (k + 1) cell grid with the hero spanning k × k cells, so the hero is 3×, 4×, 5× and 7× a small tile respectively. A hero exactly twice the size of a small tile on a uniform grid can only leave 5, 8, 11, 12, 14 or 16 companions, so a strict "2× hero" cannot yield 7 or 9. On a 1080p TV "1 + 15" gives 240 × 135 px companions for a 960 × 480 stream. The maths is tested (`GridGeometryTest`); the question is whether this family is the one wanted, or whether 2×-hero layouts with 8 / 11 / 14 companions should replace it.
- **Cached-process footprint.** After Back the process stays cached at roughly 45 MB PSS, above the 30 MB the brief asked for. 35 MB of that is shared framework pages (`.so`, `.jar`, `.art`) attributed proportionally; the app's private footprint in that state is about 0.6 MB of data plus 10 MB of code, and it holds no sockets, codecs, views or activities. Nothing in the app can shrink the shared part. Either accept the measured outcome or lower the code size with a tighter R8 configuration.

- **Phone drag on the playback bar does not accelerate.** Round 4 asked for the accelerating hold "or the phone's drag". A drag is an absolute scrubber (the finger's position *is* the time) and the debounce applies to it, but it does not step 10 s → 15 min like a held key, because a finger already covers the whole day in one gesture. If a relative, accelerating drag is wanted anyway (e.g. a slow drag near the thumb for fine seeking), `TimeBarView` has the press/drag/release hooks for it.

## Needs a real TV

- **Confirm the API-29 native-heap fix on the MiTV.** Round 3 found the grid growing the native heap by ~3.9 MB/min on the Android 10 TV, caused by the keyframe pool switching `MediaCodec` output surfaces ~24 times a second. The pool now decodes to buffers and paints a bitmap, so there are zero `setOutputSurface` calls; the emulator shows a flat native heap and one pool codec. The TV itself has not been re-measured since. Recipe: install the release APK, stream the grid for 3 min, `dumpsys meminfo com.itsluminous.hikviewer | grep 'Native Heap'` every 60 s (expect flat), `top` (expect `logd` far below the 61 % seen before, `media.codec` lower), `logcat -s KeyframePool TilePlayer` (expect one `codec #1` line, no `recreating`, hardware refusals spaced 5 / 10 / 20 … s).
- **Thumbnail upload cost: tried both fixes, neither is the cost.** On the emulator (swiftshader) the keyframe stills cost RenderThread ~16 % of a core for 13 tiles because each bitmap is uploaded through software GL. The MiTV disagrees (round 6, 16 tiles, 8 of them stills): `gfxinfo` reports 68-76 % janky frames at idle, almost all of them `Slow issue draw commands`, p50 22 ms (round 5 measured 7.8 % janky with 4 still tiles). Input is unaffected (key to dispatch 3-20 ms), but the UI's own frames pay for something. Round 10 tried the two fixes this entry proposed, release builds of the same commit on the MiTV with the 16-camera 4 x 4 grid (8 software live tiles, 8 stills), 60 s warm-up and a 120 s `gfxinfo` window, two runs each, against four runs of the unchanged build (48.8 / 54.6 / 55.9 / 49.7 % janky, p50 16-18 ms, p90 31-34 ms, `Slow bitmap uploads` 24-38 of ~1120 frames, `Slow issue draw commands` 532-617, app 88-93 % of a core, PSS 98-100 MB): (1) stills capped at 320 px for tiles narrower than 480 px (a 4 x 4 cell is 478 px, so 320 x 179 drawn upscaled 1.5x; wider cells kept 480) gave 52.9 / 54.9 % janky, p50 17-18 ms, `Slow bitmap uploads` 22-29, app 74-79 %, PSS 92-98 MB, and the stills' edge energy relative to the live rows in the same screencap fell from 0.81-0.89 to 0.61-0.70, a visibly softer picture for no jank; (2) the same plus `Bitmap.copy(HARDWARE)` on the pool's thread so the ImageView draws an already uploaded texture gave 62.1 / 58.6 % janky, p50 20 ms, p90 42 ms, p99 77-109 ms, `Slow bitmap uploads` 3-4 (the upload did move off the render thread), `Slow issue draw commands` 626-678, app 84-90 %: worse, because every still now allocates a gralloc buffer and the hardware bitmap's import into the render thread's GL context costs more than the 115 KB texture copy it replaces. Both were reverted; the code keeps `STILL_MAX_WIDTH = 480` and the RGB_565 bitmap pair (the tile-width rule and its tests are kept under `.research/r10-variants/` in case a smaller still is ever wanted for its CPU saving alone). `dumpsys gfxinfo framestats` on the TV says where the 16-20 ms frames actually go: vsync to animation 0.4 ms, UI thread 0.9 ms (p90 3.4), sync (where bitmap uploads are counted) 1.0 ms (p90 1.7), issue draw commands to the end of `eglSwapBuffers` 13.9 ms (p90 30.7, max 85), swap to frame complete 1.4 ms, dequeue 0.2 ms. So the render thread spends ~14 ms per frame issuing and flushing Skia's draw of the window, not uploading or waiting for a buffer. The device sets `debug.hwui.render_dirty_regions=false` (with `debug.hwui.use_buffer_age=1` and `EGL_KHR_partial_update` present), which makes hwui redraw the whole 1920 x 1080 window for every still instead of the one 478 x 268 tile that changed: 16 tiles, their overlays and 8 SurfaceView hole punches, ~9 times a second (the frame count is 1105-1134 per 120 s, i.e. the 8 stills a second plus a few UI frames), on a GPU that SurfaceFlinger is also using. What would help is fewer app frames, not cheaper ones: coalesce the eight tiles' still swaps into one `post` per second (one frame instead of eight, the same window redrawn once), or draw a still-only tile's picture into its own idle `SurfaceView` via `lockCanvas` so SurfaceFlinger composes it like a video layer and the app window is not redrawn at all (round 3 moved stills off the surfaces because the pool then lent the surface to a shared decoder; a `lockCanvas` still does not have that problem, but a promotion to live must cope with a surface that already holds a picture). Measure either with the round 10 recipe (`.research/TV-R10.md`) before keeping it; the bar is the same 10 points of janky %.
- **Idle headroom at 12 fps.** With 16 tiles (8 live, 8 stills) the MiTV has 13–19 % idle CPU, below the 35 % the budget asks for before probing above its ceiling (25 % was tried and churned: one more software tile costs 12–17 points of the reading, so a promotion at 25 % was shed within a minute), so at the recorder's current 12 fps nothing changes on this TV. Lowering the sub-stream to 6–8 fps (the user's plan) is what makes the probe fire; verify then that it settles at 10–12 live without relapsing (`live budget: promote, limit=9 above the ceiling (idle=…)` and no `demote, idle=…` within the hour).
- **Move mode with the physical remote.** `input keyevent --longpress` delivers a plain click on this API 29 TV, so the shell cannot open the tile menu; the cap to the hero's decoder during a move (`hardwareOnly`) is covered by Robolectric and Espresso only. Hands-on: hold OK → *Move* → every other tile should drop to stills within a second and come back live on OK or Back.
- **Hardware slots in flat grids: tried and reverted.** Round 6 gave the first two tiles of a flat grid the TV's two idle hardware decoders (8 % of a core each against 22 % for software). Measured twice on the MiTV with the 16-tile grid: the `OMX.MS.AVC.Decoder` fed through the jitter buffer put its pictures out at 83 ± 60 ms (max 205–214 ms) while the paced software tiles beside it showed 83 ± 18–24 ms, and the idle share did not move (6–26 % against 8–23 % before), so the two tiles were visibly jerkier for nothing. Reverted the same day; the hardware decoders stay with the hero and the single-camera screens, unpaced. If the slots are wanted in a grid, first find out why the hardware decoder's output is uneven when fed one picture at a time (output buffer count held by SurfaceFlinger at the 15 Hz slot? an internal pipeline that flushes in pairs?) and measure an unpaced hardware tile in a grid for comparison.
- **CPU budget on the 1.7 GB TV.** Before the round-3 fixes the TV sat at `media.codec` 137–157 % and app 43 % of one core with 8 live software tiles (budget ≤ 150 % / ≤ 40 %). The fixes removed two churn sources (surface switching, hardware retries every 5 s) but the TV has not been re-measured.

- **Overlay fix confirmed on the MiTV (round 5, 16:40).** The round-5 one-dot / missing-focus-border symptom came from the Android ≤ 11 `SurfaceView` hole punch (`drawColor(CLEAR)` over the clip) meeting the tile's `clipChildren = false`; with the fix (clipped tiles, media-overlay surfaces, an inset border overlay drawn last) a 4 × 4 grid on the TV shows sixteen green dots top-right and the eight keyframe tiles show their stills (a screenshot scan found 140–170 green pixels in every tile's top-right corner and no black tile). The same wipe had hidden the keyframe stills, which the pool had been delivering all along (`KeyframePool` / `TilePlayer … still #N` logs).
- **Leaving the grid stops eight codecs on the main thread.** `surfaceDestroyed` → `TilePlayer. attachSurface(null)` releases the tile's decoder synchronously (deliberately: the surface is about to be freed and a codec drawing into a freed surface crashed the emulator). On the MiTV the watchdog measured that traversal at 400–520 ms when opening fullscreen or settings from a grid of eight live tiles, a visible hitch on the transition, not during streaming. An alternative that keeps the safety: hand the release to `DecoderReleaser` and have `surfaceDestroyed` wait on the future with a short timeout, or `MediaCodec.setOutputSurface` to a dummy surface first on API 23+.
- **`RenderPacer` is tuned for one composer.** The 15 Hz shared cadence for software tiles exists because the MiTV's composer takes one overlay and GPU-composites the rest. A TV whose composer takes all 17 layers gains nothing from it and loses 0–67 ms of live latency per picture; a 25 fps camera is shown at 15 fps in a tile. If that matters, derive the slot from the measured frame rate or disable pacing when `dumpsys SurfaceFlinger` would show every layer as `DEVICE` (not readable from an app: the only in-app proxy is the HWUI GPU stage time from `FrameMetrics`).
- **A 4-minute TV-wide freeze seen once.** During round 4 (12:28, first install of the live-dot build) the MiTV stopped logging from every process for four minutes right after launch; `lowmemorykiller` had just killed nine cached processes and the load average was 67 afterwards. The app survived and its streams reconnected; the freeze was not reproduced in the following runs. Memory headroom with the grid up is ~90–120 MB free. If it recurs, capture `dmesg`/`lowmemorykiller` lines around it.
- **Cold start on the MiTV demotes a tile or two for a couple of minutes.** In the round-4 final run (release build, 12 cameras in 4 × 3, 8 live) the first three minutes after a fresh process start showed back-to-back ART concurrent GCs of 1–3 s each (heap 17 → 20 MB, ~2.5 MB/s allocated by the demux/decrypt pipeline: a `ByteArray` per NAL plus a copy per encrypted NAL) on a saturated 4×A55; three software decoders fell 15–19 pictures behind at once, the budget demoted to 4 live and promoted back to 8 within two minutes, after which GCs were 80–440 ms and nothing stalled for the rest of the run. Working as designed, but a pooled NAL buffer (or decrypting in place also for TYPE_HINT, which currently copies) would cut the allocation rate and likely the warm-up dip.
- **App CPU with many software tiles.** With 7 software-decoded tiles the app process itself (not `media.codec`) ran at 60–100 % of one core on the 4×A55 TV: the decrypt/demux pipeline scales with tiles. The round-3 CPU notes list what was tried; the next candidates are the AES calls per NAL (one `Cipher.doFinal` per 16-byte probe block plus one per body) and the RTP reassembly copies.

- **Round-7 playback on real recordings.** The keyframe gate and the `PlaybackStepper` were verified on the TV only in the debug demo mode (the recorder was offline): -10x for 60 s gave no spinner and no green picture, +10x ran to "End of recordings". With the recorder back: -10x, +10x and repeated seeks for 60 s each on HEVC 720p recordings, screen chroma check, and the stepper's `late` / `failed` counters in the `PlaybackViewModel` log line. If the relay turns out to deliver a window faster than real time, a longer `PlaybackStepper.WINDOW` would serve several steps per fetch (the class already keeps such a window open).
- **`PresentationRate` on the MiTV.** The policy (software grid tiles present every second picture above 8 tiles, the hero always at full rate) is plumbed and tested but switched off (`PresentationRate.ENABLED`). It saves composition only, never decoding. Round 9 measured it on the 1 GB Android TV AVD (`HikViewer_TV_1GB`, 4 cores, API 34, swiftshader) with the real account and 16 cameras in the 4 x 4 layout, off vs on, 3-minute windows after a 60 s warm-up, the other emulators shut down and the host idle: off = `gfxinfo` 93.6 % janky (legacy 6.1 %), p50/p90/p99 17/23/48 ms, app 27 %, mediaswcodec 48 %, SurfaceFlinger 2.9 %, composer 3.2 %, PSS 84 MB, 6 live tiles at 12 fps; on (two runs) = 85.3 % / 89.5 % janky (legacy 6.8 % / 6.8 %), p50/p90/p99 18/25/81 and 17/27/48 ms, app 23 % / 30 %, mediaswcodec 39 % / 45 %, SurfaceFlinger 1.1 % / 1.2 %, composer 2.7 % / 2.7 %, PSS 92 / 98 MB, 5 live tiles at 6 fps (`present=1/2`), and in 1 + 15 the hero stayed `present=1/1` at 12 fps. Decision rule: enable only if janky % drops by 10 points or more, or SurfaceFlinger + app CPU by 15 % or more, with no hero fps regression. Janky fell 4 to 8 points and SurfaceFlinger + app CPU went from 30 % to 24 % and 31 % (one run down 19 %, the other up 3 %), so the switch stays off. The emulator is not the TV: its composer is swiftshader in software (SurfaceFlinger idles at 1 to 3 %, so there is almost nothing for the policy to save), the MiTV composes on a Mali GPU where round 6 saw 56 to 76 % janky frames, and the headline janky % on the emulator is saturated by "slow issue draw commands" on nearly every UI frame, so only the legacy janky %, the percentiles and the CPU columns were comparable. Round 10 repeated the comparison on the MiTV-MOOQ1 itself (Mali-G52 composer, 16 real cameras in the 4 x 4 layout, 8 software live tiles plus 8 stills, release builds of the same commit, 60 s warm-up then a 120 s `gfxinfo` window, interleaved off, off, on, on, off, off): off = 48.8 / 54.6 / 55.9 / 49.7 % janky (mean 52.2), p50 16 to 18 ms, p90 31 to 34 ms, p99 48 to 57 ms, SurfaceFlinger 21 to 22 % + app 90 % of a core (112 % together), PSS 98 to 100 MB, live tiles `present=1/1` at 12 to 13 fps; on = 40.7 / 44.8 % janky (mean 42.8), p50 14 to 15 ms, p90 29 to 30 ms, p99 48 ms, SurfaceFlinger 17.5 to 18 % + app 83 % (101 % together), PSS 90 to 93 MB, the eight live tiles `present=1/2` at 6 fps, 16 green dots and 16 tiles with content in every run, key latency 4 to 20 ms in both arms. That is 9.4 points less jank and 9.6 % less SurfaceFlinger + app CPU: under the 10-point and 15 % bars, so the switch stays off on the real TV too. It is the closest the policy has come and the gap to the bar is one noisy run wide, but what it buys is a 6 fps picture on eight tiles, and the `framestats` breakdown in the entry above says the janky frames are the app window being redrawn whole for every still, which halving the live tiles' presented rate only dilutes. Do not re-measure once the recorder runs at 6 to 8 fps (the policy would then show 3 to 4 fps); re-measure with the same six-run sequence only after the still redraws are fixed, the diagnostics lines (`present=1/N`, `fps=`, `shown[]`) are in place for it.

## Code and tests

- **`androidx.security:security-crypto` is deprecated as of 1.1.0.** AndroidX stopped the library (Tink-backed `EncryptedSharedPreferences` and `MasterKey`) with no successor artifact; `AppGraph.encryptedPrefs` carries a `@Suppress("DEPRECATION")` with the reason. The session and the verification code are stored in its on-disk format, so replacing it (a `KeyStore` AES key wrapping the values, or the Tink `AndroidKeysetManager` directly) needs a one-time migration that reads the old preferences before the first write. The library still works and gets no new releases; nothing forces the move until a `targetSdk` or Tink change breaks it.
- **No memory guard under an explicit live-camera count** (moot since 0.2: the *Live cameras* Settings row is gone and the grid always passes `setLiveCeiling(null)`; the note stays for the API, which `LiveBudget.setCeiling` keeps). `LiveBudget.sample` counts low spare memory (and low idle CPU) as lag only while `liveLimit > ceiling`, that is for a tile probed above the automatic ceiling, and `PlaybackCoordinator.probeIfWorthIt` stops the `HeadroomProbe` for an explicit ceiling, so a 1 GB TV given 16 would be shed by decode lag alone: 2 s of lag, then one tile per 10 s. If an explicit ceiling ever returns, keep the probe running while `ceiling > automaticCeiling` and apply the `LOW_MEMORY_BYTES` rule, not the idle rule (which would fight the choice), to the tiles above the automatic ceiling.
- **`GridActivity.updateLiveCount` recounts every player on each liveness change** (O(n²) over 16 tiles, at most twice a second per tile). Harmless today; a counter maintained incrementally would be cleaner.
- **One INFO line per key press in release builds** (`GridActivity.dispatchKeyEvent`, "reached the grid N ms after the press"). It is what a TV logcat is read for when the remote feels slow and costs nothing per frame; logging only when the wait exceeds 50 ms would keep the signal and drop the noise.
- **`CpuHeadroomProbe.stop()` does not join its thread.** A burst in flight finishes after the stop; its sample is discarded by a generation check, so the reading is right, but the thread can outlive the probe by up to a second.
- **`scripts/tv-login.sh` passes the credentials through `tv.py`'s argv** (visible in `ps` for the call's duration) and uses fixed `sleep`s. A local development script, same model as `emu-login.sh`; fine while it stays that.
- **`TileDecoder`'s pacing path has no unit test of its own.** `FramePacer` is tested with a fake clock and the TV run shows `paced=6-8 rebuffers=0 catchUps=0`, but the glue (admitting due pictures on the codec-callbacks looper, the one-wake-up-at-a-time rule, `queuedFrames` counting only due pictures) runs only on a device because the class owns a `MediaCodec`. Extracting the input queue into a pure class would let it be tested.
- **`PlaybackCoordinator.stop()` does not emit a new player list**, so the grid's tile collectors keep observing released players until the next bind. They are `StateFlow` collectors and cost nothing, but a terminal emission would make the lifecycle easier to reason about.
- **Large files.** `NalDecryptor.kt` (~490 lines) and `PlaybackViewModel.kt` (~450 lines) are past the "small files" guidance. The decryptor's three key variants could become three small strategies; the playback view model could split the transport (window reopen, hop timer) from the UI state.
- **Phone Espresso suite is thin.** `PhoneNavigationTest` has two tests: the persistent bar, and the portrait camera screen with a swipe and a bar scrub. The speed toggle, the date chip and landscape on a phone are only covered by Robolectric.
- **`H264SpsRewriter` assumes no B-frames.** It declares `max_num_reorder_frames = 0` for every H.264 stream, which is true for this recorder (P-frames only, order count growing within a GOP; ffmpeg frame md5s are identical before and after) and what stops libavc holding ten pictures. A recorder that emits B-frames would display them out of order and nothing would say why. The SPS alone cannot tell; a guard would have to watch the order count of the first slices of a GOP and skip the rewrite when it ever goes backwards.
- **Two clocks in the player stack.** `PlaybackViewModel` ticks with `System.nanoTime()` (so the render timestamp handed to `MediaCodec` is on the same clock SurfaceFlinger uses) while the rest of the view model runs on `uptimeMillis()`. Giving `TilePlayer.tick` the injected clock would make the tests and the code read from one time source.
- **Small leftovers from the round-4 review.** `SeekController.isHolding`/`reset()` are only used by tests; three log tags (`HikViewer`, `TilePlayer`, `LiveBudget`) cover one subsystem, one prefix would make a TV logcat easier to grep; a tile dropped from the layout keeps its `onSurface` hook until it is re-bound (harmless, the player is stopped).
- **Verification dialog over the grid.** While the "video encryption password" dialog is open the tiles underneath keep decoding. The dialog is up for seconds, so the saving was judged not worth a covered-tile signal from the UI into the player; revisit if the dialog ever stays open longer.

## CPU ideas set aside, worth revisiting if the numbers change

These were measured or reasoned about in round 3 and not adopted; the reasons are recorded so the next person does not repeat the work blind.

- **`Surface.setFrameRate`, `KEY_OPERATING_RATE`, `KEY_PRIORITY`.** Not measurable on the emulator (the goldfish / `c2.android` decoders ignore them) and the target TV runs API 29 where `setFrameRate` does not exist. An unmeasured hint to a vendor OMX decoder risks lower frame rates for no proven gain. Worth a trial on an API 31+ TV with a hardware decoder.
- **Smaller or opaque SurfaceViews.** Already opaque; the buffer size is set by the decoder, not the view, and SurfaceFlinger scales the 960 × 480 buffer onto the tile. A smaller view saves nothing in decode. Only a smaller sub-stream on the recorder changes this.
- **One NIO selector thread for all relay sockets.** Threads blocked in `recv` cost no CPU; the cost is per byte and per syscall, which the 64 KB buffered reads already address. A selector rewrite of `VtmRelayClient` would remove ~12 idle threads at considerable risk in the one component the real-account tests exercise.
- **Collapsing the `flowOn(Dispatchers.IO)` hop per picture.** About 144 channel hand-offs per second across 12 tiles, below the measurement noise floor.
- **Dropping P-frames.** Impossible: they are reference frames. Keyframe-only mode is the only valid reduction and already exists.
- **Lowering `STILL_MAX_WIDTH` or uploading stills as hardware bitmaps** (see "Thumbnail upload cost" above: measured on the MiTV in round 10, neither moves the janky %).
